Як працює Tempo

Браузер надсилає план, API ставить розрахунок у чергу, а воркери шукають кращий розклад. Нижче — хто за що відповідає і як між ними рухаються дані.

Шлях одного розрахунку

  1. 01

    Ти задаєш план

    Вводиш задачі, дедлайни, залежності та доступних виконавців.

  2. 02

    API перевіряє дані

    Балансер обирає API. Той перевіряє вхід, параметри й ліміти.

  3. 03

    Розрахунок у черзі

    Параметри зберігаються в PostgreSQL. Якщо воркери зайняті, показується очікування.

  4. 04

    Воркер обчислює

    Забирає вільний розрахунок і запускає Python-оптимізатор в окремому процесі.

  5. 05

    Результат у браузері

    Прогрес і готовий план проходять через API та балансер до діаграми Ганта.

Що роблять балансер і два API

Python-балансер — єдина точка входу. За правилом least_conn він обирає API з меншою кількістю активних запитів. Якщо значення однакові, сервери чергуються.

API_1 та API_2 мають однаковий код на Node.js та Express. Вони перевіряють користувача, створюють розрахунки й повертають історію та результати. Обидва працюють зі спільною базою й ключем токенів.

Відкрите з’єднання для прогресу теж враховується балансером. Важкий пошук розкладу виконують воркери.

Що зберігає PostgreSQL

ТаблицяЩо в ній

jobsЧерга, вхідні параметри, статус, прогрес і результат кожного розрахунку.

Черга повністю зберігається в PostgreSQL. Redis і RabbitMQ не використовуються.

Воркер і його обчислення

Воркер бере один вільний розрахунок із черги та запускає дочірній Python-процес. У ньому оптимізатор шукає кращий порядок задач і розподіл між виконавцями.

Основний воркер записує прогрес у базу, перевіряє скасування та контролює тайм-аут. API читає стан приблизно кожні 750 мс й передає зміни браузеру через SSE — тривале з’єднання для оновлень.

12 задач і 3 виконавці у формі — це один розрахунок, який обробляє один воркер. Виконавці в плані — люди або обладнання, чию роботу ми плануємо.

Як з’являються додаткові воркери

Autoscaler оцінює чергу й визначає потрібну кількість: від двох до чотирьох. Значення зберігається в settings.

Supervisor читає це налаштування та запускає резервні процеси WORKER_3 і WORKER_4. Коли попит знижується, приблизно через 20 секунд ціль повертається до двох. Резерв завершує поточну роботу перед виходом.

Наприклад, із шести важких розрахунків чотири виконуються, а два очікують у черзі.

Як оптимізується розклад

Спочатку будується допустимий початковий план. Потім імітація відпалу перевіряє інші порядки задач і призначення виконавців, зберігаючи найкращий знайдений варіант.

Один виконавець робить одну задачу за раз. Залежна задача починається після завершення всіх попередніх. Ціль: тривалість плану + 2 × сумарне запізнення.

Глобальний оптимум не гарантується. Час рахується безперервно; години на кшталт 14:00 є способом відображення відліку від початку плану.

Як це запущено зараз

Локально компоненти працюють окремими процесами на одному комп’ютері. Браузер відкриває вхід балансера: HTTP 8088 або HTTPS 8443 за наявності сертифіката. API використовують порти 3101 і 3102.

Панель «Стан системи» показує живі показники API, балансера та воркерів. Ця сторінка пояснює їхню будову й зв’язки.

Docker є альтернативним способом запуску. У поточній Docker-конфігурації чотири контейнери воркерів створюються заздалегідь; нові контейнери автоматично не створюються.

Трохи глибше: черга, ліміти та відновлення

Воркер одним SQL-запитом змінює статус вільного розрахунку на running. FOR UPDATE SKIP LOCKED дозволяє пропускати записи, які вже забирає інший воркер.

UPDATE jobs AS job
SET status = 'running', worker_id = %s, attempts = attempts + 1
FROM (
  SELECT id FROM jobs
  WHERE status = 'queued' AND cancel_requested = false
  ORDER BY created_at, id
  FOR UPDATE SKIP LOCKED
  LIMIT 1
) AS next
WHERE job.id = next.id
RETURNING job.*;

Перевірка ліміту активних розрахунків проходить у транзакції з блокуванням рядка користувача. Запис результату перевіряє поточний статус, воркера та номер спроби, щоб пізній результат не перезаписав скасований або повторно запущений розрахунок.

Типові межі: 80 задач, 8 виконавців, 2 млн ітерацій і 6 активних розрахунків на користувача. Тайм-аут — 120 секунд. Після втрати heartbeat воркера розрахунок можна повернути в чергу; максимум три спроби.
